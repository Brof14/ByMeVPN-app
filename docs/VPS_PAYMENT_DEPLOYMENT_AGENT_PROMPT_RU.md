# Задание для AI-агента с доступом к VPS: ByMeVPN — полностью работающие платежи YooKassa и Crypto Pay (@send)

Ты senior backend/SRE/fullstack engineer. Выполни задачу, а не ограничивайся аудитом. У тебя есть доступ к работающему VPS Ubuntu, исходникам бота и Android-клиента. Не уничтожай активных подписчиков, VPN-ключи, базу и чужие данные. Сделай резервные копии перед изменениями, проверь возврат к рабочей версии и фиксируй результат тестов.

## Исходные факты (сверь с реальным сервером)
- Backend: https://github.com/Brof14/ByMeVPN_bot, Python/FastAPI, файлы `api_router.py`, `payments.py`, `payment_monitor.py`, `webhook.py`, `database.py`, `constants.py`, `config.py`; на VPS исторически `/opt/ByMeVPN_bot`, Docker Compose.
- Android: https://github.com/Brof14/ByMeVPN-app, активные изменения в PR #8, класс `YooKassaPaymentHandler.kt`, `PricingScreen.kt`, `ByMeApiClient.kt`.
- Backend PR https://github.com/Brof14/ByMeVPN_bot/pull/17 добавляет `/plans?devices=2|5|10`, корректный расчёт и подтверждение устройства. НЕ делай предположений, что PR уже смёржен и развёрнут: проверь SHA работающего контейнера.
- У backend уже есть интеграции `create_yookassa_payment`, `create_crypto_payment` (Crypto Pay API), мониторы обеих систем, выдача через 3x-ui и безопасный журнал платежей; переиспользуй их, а не создавай параллельную систему.
- Сейчас `POST /api/v1/payment/create` принимает в основном `provider=yookassa` и отклоняет `crypto`. `GET /api/v1/payment/check` умеет проверять оба провайдера при наличии записи о счёте.
- Секреты: `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `CRYPTO_BOT_TOKEN`, `JWT_SECRET`, `WEBHOOK_URL`, `WEBHOOK_HOST`, `WEBHOOK_PORT` хранятся в .env/секретном хранилище; НЕ печатай их в логи, ответы, PR или чат.
- Проект ранее запускался через `cd /opt/ByMeVPN_bot && docker compose ...`; сначала проверь реальное расположение, текущие контейнеры, volume, базу, сертификаты, reverse proxy и конфигурацию.

## Что необходимо реализовать

1. **Сделать сервер источником истины о цене.** Все сочетания периодов 1, 3+1, 6+2, 12+3 месяцев и лимита 2/5/10 устройств должны давать подтверждённые сервером `plan_code`, `days`, `devices`, `amount_rub`. Никакие клиентские `amount_rub/days/devices` не могут принудить сервер выставить неверную сумму. Сервер валидирует принадлежность платежа user_id и тариф. Совмести Android и backend контракты.

2. **YooKassa.** Проверь наличие и работоспособность реальных merchant credentials без раскрытия секретов, sandbox/test и production режимы. Создавай платёж идемпотентно по уникальному server-side `request_id` с `Idempotence-Key` и корректными метаданными user_id, plan, devices, days, RUB. Показывай пользователю `confirmation_url` через безопасный внешний браузер/Custom Tabs. Реализуй (или почини) webhook HTTPS и резервный polling; webhook нельзя считать доказательством оплаты без проверки статуса по официальному API YooKassa, валюты, точной суммы, ID и принадлежности. Обрабатывай succeeded/canceled/pending, задержки, повторный callback и рестарты.

3. **Crypto Bot @send — Crypto Pay API.** Используй уже существующий `CRYPTO_BOT_TOKEN`, методы `createInvoice`, `getInvoices`/получение статуса; сверяй актуальные поля с https://help.send.tg/en/articles/10279948-crypto-pay-api . Поддерживай `provider=crypto` в том же мобильном API создания и проверки платежа. Создавай инвойс с `currency_type=fiat`, `fiat=RUB`, ценой тарифа и допустимыми криптоактивами; сохраняй invoice_id, owner user_id, устройства, срок, точную цену и статус до выдачи. Существующий `CryptoPaymentMonitor` должен корректно завершать выдачу после `paid`, включая счета, оплаченные во время падения VPS. Допустим webhook с обязательной проверкой подлинности, либо надёжный polling. Не доверяй клиентскому признаку `paid` и не бери цену из payload клиента.

4. **Единая выдача VPN-подписки.** После доказанного успешного платежа строго один раз продлить подписку нужного пользователя, создать/обновить клиент в 3x-ui с правильным числом устройств и временем, актуализировать `/subscription/status`, `/me`, `/devices` и учёт в Telegram-боте. Обработать одинакового пользователя на Android и в Telegram без двух отдельных аккаунтов/ключей. Если оплата прошла, а 3x-ui временно недоступен, записывать `paid/fulfillment_pending` и повторять идемпотентную выдачу с оповещением поддержки; никогда не терять платёж и не выдавать дважды.

5. **Android.** После готовности backend добавить в `PricingScreen` честный выбор между YooKassa и `Crypto Bot (@send)` и ровно те варианты, которые реально поддерживает API. Передавать `provider`, `plan_code`, `devices`, `request_id`. Кнопка без работающего провайдера должна быть отключена с объяснением. Отобразить промежуточные статусы `pending / processing / succeeded / failed`, возможность повторной проверки, ошибки и безопасный возврат в приложение через deep link. Не объявлять успех при открытии страницы оплаты. Никаких двойных платежей при повторном нажатии.

6. **Google Play — критическое ограничение.** Перед включением YooKassa/Crypto Pay внутри версии, распространяемой через Play, проверь официальную Google Play Payments policy https://support.google.com/googleplay/android-developer/answer/9858738 . Для цифровых подписок Play Billing обычно обязателен, кроме применимых исключений или официального участия в альтернативной биллинговой программе. НЕ маскируй внешнюю оплату от Google и не внедряй неразрешённые ссылки. Предусмотри разрешённое решение (например, Play Billing для Play flavour; YooKassa/Crypto для direct APK и сайта), сохраняя единую систему прав доступа.

7. **Качество, безопасность и эксплуатация.** Таймауты, retry/backoff, структурированные не содержащие токенов логи, защита callback, индексы/unique на provider+invoice_id и request_id+user_id, транзакционный ledger, check ownership, постоянное хранение, трассировка без утечки банковских данных. Не ломай существующий Telegram checkout и бесплатный 3-дневный период. Автопродление подключать только при явном согласии клиента и разрешении магазина; никаких скрытых подписок.

## Последовательность работы
1. Аудит реальных рабочих контейнеров/логов и точного git SHA (без раскрытия секретов). Snapshot БД + volume + конфигов, проверка restore.
2. Локальные правки через GitHub PR/коммиты, Python unit + integration tests с mock YooKassa/Crypto Pay, тесты существующей выдачи 3x-ui. Тесты ошибок, сетевых таймаутов, дубликатов webhook, рестартов и смены лимита устройств.
3. Тестовые платежи обоих провайдеров по возможности в sandbox/test окружении (не списывать реальные деньги без отдельного согласования). Привести работающий тариф каждого из лимитов 2/5/10; проверить фактическую БД, ключ/expiry/HWID и Android-статус.
4. Согласованный rollout: backend первым, затем клиент. Пересборка контейнеров `docker compose up -d --build` только после проверки volume/.env и плана отката; healthcheck, API smoke tests, платежные monitor logs, подтверждение работающего Telegram-бота и VPN пользователей.
5. В финале выдай отчёт: файлы и SHA коммитов, diff, контракт API, реальные URL только без токенов, тесты, статус обоих способов оплаты, ограничения Google Play, команды отката. Отдельно перечисли то, что нельзя было проверить без мерчант-доступа.

**Правило завершения:** не пиши «платежи полностью работают», пока не подтверждены создание инвойса, оплата, обработка статуса, успешная выдача в 3x-ui и повторная проверка подписки. Не редактируй продакшен-секреты без необходимости.
