# Android: результаты аудита и оставшиеся проверки

## Актуализация 21.11.2026 — Android 1.0.50

В текущем `ByMeVpnService` TUN настраивает IPv4-маршрут `0.0.0.0/0` и IPv6-маршрут `::/0`. Старые ниже приведённые пункты описывают состояние прошлых версий и не являются текущим подтверждением утечки или отсутствия маршрута. Наличие маршрутов в коде само по себе не доказывает, что IPv4, IPv6 и DNS-трафик действительно идут через туннель на устройстве.

Релиз 1.0.50 добавил параллельные проверки задержки с ограничением до четырёх узлов и таймаутом native-вызова, а также SBOM для Gradle-зависимостей в CI и релизах. Встроенный `libv2ray.aar` остаётся бинарной зависимостью с неподтверждённым upstream source/toolchain; отдельный provenance-файл явно фиксирует этот пробел.

Остаются непроверенными на реальных устройствах: маршрутизация IPv4/IPv6 и DNS, переподключение при смене сети, Hysteria, фоновые ограничения Android, upgrade поверх установленной подписанной версии и поведение сетевого пинга на разных устройствах.

## Историческая запись: актуализация 15.11.2026 — Android 1.0.32

- Проверка Telegram-сессии в Android выполняется только `POST`; одноразовое состояние больше не помещается в query-параметр даже при ответе backend `405`.
- Проверка туннеля на старте и во время работы использует несколько независимых HTTPS-узлов. Один недоступный сайт больше не считается отказом VPN; служба отключает туннель только после трёх подряд неудачных циклов, когда не отвечает ни один узел.
- При завершении процесса служба теперь восстанавливает только ранее активный туннель или системный Always-on VPN. Секретная конфигурация не сохраняется для восстановления: клиент заново запрашивает статус и серверную конфигурацию. Явное отключение очищает флаг восстановления.
- Удалён фиктивный API настройки блокировки рекламы: он всегда возвращал `false` и ничего не включал.
- Одноразовое фоновое обновление после получения списка серверов теперь принадлежит scope API-клиента; изменения настроек используют scope singleton-репозитория, а deep-link подтверждение платежа — lifecycle Activity.
- Создание платёжной сессии и открытие checkout теперь выполняются в coroutine scope экрана/вызова; закрытие экрана отменяет незавершённый запрос, вместо оставления фоновой задачи с устаревшим UI callback.
- Ручной `currentScreen` заменён на Navigation Compose back stack: системный Back возвращает к предыдущему экрану, тарифы и поддержка сохраняют точное происхождение, маршрут и аргументы сохраняются через Android state restoration.
- Внешний профиль теперь загружает узлы и конфигурации только из своего импорта/HTTPS-feed, не вызывает авторизованные endpoints ByMeVPN и сохраняет импорт при истёкшем аккаунтном токене. При восстановлении службы исход однозначно завершается как `RESTORED`, `FAILED` или `CANCELLED`, а неуспешное восстановление убирает foreground-уведомление.

Изменения проверяются CI и unit-тестами. Без телефона остаются непроверенными фактическая маршрутизация приложений через TUN, IPv6 и DNS на разных сетях, реальный перезапуск службы/Always-on/kill switch, запуск Hysteria и скорость соединения. Эти сценарии нельзя объявлять подтверждёнными по unit-тестам.

Остальные ограничения аудита остаются в следующих областях: доказательство IPv4/IPv6/DNS-защиты; разбиение крупных экранов и выделение ViewModel; единая ресурсная локализация и полный UI-тестовый набор; проверка происхождения `libv2ray.aar`; профилирование и обновление APK на установленном устройстве; сквозные платежи и управление автопродлением. Для последних нужны тестовая среда платёжного backend и устройство; код клиента не может сам подтвердить корректность production webhook или списания.

Исторические заметки ниже сохранены как записи прежних проверок. Их результаты и версия клиента не описывают текущий релиз.

## Актуализация 15.11.2026 — Android 1.0.27, изменения по аудиту

Этот блок описывает текущую проверку исходников. Исторические отчёты ниже сохранены для контекста и не должны использоваться как описание текущего состояния без повторной проверки.

- Внешняя ссылка `bymevpn://sub` больше не импортируется автоматически: приложение показывает домен источника и предупреждение, требует явного подтверждения, запрещает замену серверов авторизованного аккаунта и не отправляет внешнему хосту HWID/модель устройства. После подтверждения она работает только в отдельном локальном профиле без токена аккаунта; подключение опирается на импортированные узлы и срок подписки, а не на ByMeVPN entitlement.
- Импорт подписки ограничен 1 MiB, 256 строками и 64 конфигурациями; URL с user-info или fragment отвергается, HTTP-перенаправления не выполняются.
- Ссылки, полученные от backend, отдельно помечаются в зашифрованном хранилище; только они могут получать заголовки подтверждения устройства. Старые сохранённые ссылки считаются недоверенными.
- Ручной/автоматический выбор сервера теперь имеет общий сохраняемый источник состояния. Если выбранного узла больше нет, клиент возвращается к автоматическому выбору. При отсутствии результатов измерения фиксируется выбор резервного первого узла, а не утверждение о минимальной задержке.
- Возврат из тарифов и помощи ведёт в экран, откуда пользователь пришёл; текущий экран восстанавливается при пересоздании Activity. Удаление устройства имеет область нажатия не менее 48 dp. Расширенные настройки доступны из раздела настроек; прямой маршрут российских сайтов описан явно.
- В тарифах изначально выбран короткий план; «лучшая цена» показывается только при наличии серверных цен для всех вариантов и рассчитывается по цене за день. Деление месячной цены округляется вверх.
- Обновлены README и этот аудит. Подписанная сборка, unit-тесты и CI не подтверждают реальный трафик через Android TUN, IPv6/DNS, восстановление после убийства процесса, интеграцию платежей, работу обновления APK или доступность каждого узла. Эти сценарии требуют физического устройства, тестового backend/магазина и разных сетей; в текущем изменении они не объявляются проверенными.

Релизная минификация не включается: сначала нужна проверка нативного Xray runtime. В репозитории остаются отдельные архитектурные задачи — полноценный Navigation Compose, разделение больших экранов/ViewModel, UI- и screenshot-тесты, профилирование, подтверждение происхождения `libv2ray.aar` и SBOM. Их нельзя считать закрытыми только по этому клиентскому патчу.

Этот документ описывает ограничения клиента на момент подготовки PR #4. Он не подтверждает состояние production и не является разрешением на выпуск.

## Остаётся до подтверждения релиза

1. **Трафик телефона.** `XrayVpnEngine.probeProxy` проверяет HTTPS через локальный SOCKS, но не проверяет путь пакетов другого приложения через Android TUN. Нужен тест на физическом устройстве: маршруты, DNS и реальные IPv4/IPv6 запросы через VPN, смена сети, потеря связи и очистка после остановки. Устройство ADB во время аудита не обнаружено.
2. **Жизненный цикл.** Служба возвращает `START_NOT_STICKY`; конфигурация следующего запуска хранится в памяти процесса. Ограниченные повторные попытки после сбоя не обеспечивают восстановления после завершения процесса, перезагрузки или длительного отсутствия сети. Проверить системный always-on VPN и ограничения фоновой работы на реальных устройствах.
3. **Маршрутизация и DNS.** Код исключает пакет приложения из собственного VPN, чтобы сокеты ядра не попадали в петлю; вызова `VpnService.protect` для отдельных сокетов здесь нет. Проверить поведение при смене сети, доступность DNS и IPv6 на устройстве, в том числе при настройке прямого доступа к российским сайтам. Нельзя считать отсутствие утечек доказанным по исходному коду.
4. **Hysteria 2.** Генерация конфигурации покрыта unit-тестом, но тест не запускает нативное ядро и не подтверждает совместимость установленной библиотеки с сервером. Нужен реальный тест туннеля, включая отказ недоступного сервера.
5. **Авторизация и устройства.** Google-вход закрыт до безопасной проверки токена сервером и подтверждения release OAuth. Совместимость Telegram-входа и `is_current` зависит от backend PR #11 и Android PR #3. Проверить владельца устройства, лимиты, добавление и удаление с тестовой панелью 3x-ui. В текущем экране устройств нет действия удаления.
6. **Платежи.** PR #3 зависит от backend PR #11 и не развёрнутого согласованного API. Требуются тестовый магазин YooKassa, проверка webhook, статуса счёта, повторных уведомлений и привязки карты. Условия распространения через Google Play и соответствующий способ оплаты нужно проверить перед публикацией.
7. **Сессия и кэш.** При некоторых ошибках обновления токена текущий API-клиент очищает сессию; сохранённые импортированные конфигурации и ссылка подписки требуют отдельной проверки при выходе и смене аккаунта. Серверный список из API в PR #4 привязан к аккаунту; старые пользовательские конфигурации используют отдельное хранилище.
8. **Offline entitlement.** В `ApiConfig.SERVER_ES256_PUBLIC_KEY` находится placeholder, а отсутствие entitlement не блокирует `canConnect`. Нужны согласованный серверный формат и настоящий публичный ключ, проверка подписи и истечения срока; до этого нельзя считать offline-проверку защищённой.
9. **Локализация и интерфейс.** Переключение языка есть, но переведены не все экраны. Необходимо проверить все действия, системный язык и доступность на устройстве. Экран устройств переведён в PR #4; это не означает завершение перевода всего приложения.
10. **Подпись и публикация.** Подписанный APK/AAB не проверены на обновление установленной версии с сохранением данных. Нужны ключ подписи, проверка идентичности сертификата, release-сборка и реальные приёмочные тесты. Зелёный debug CI не заменяет эти проверки.

## Границы PR #4

Повторное подключение ограничено пятью попытками и работает, пока процесс приложения жив. После исчерпания попыток показывается ошибка. Список API-серверов сохраняется для текущего аккаунта; свежий кэш повторно используется до шести часов, затем обновляется при следующем обращении или работающем периодическом цикле. Ошибка загрузки сохраняет доступный старый список. Это не точное фоновое расписание при остановленном процессе.

## Обновление 31.10.2026 (коммит d9cbb96)

Что сделано в клиенте:

- **Серверы до подключения.** Сохранённый список подписки показывается сразу, обновление подписки уходит в фон и больше не задерживает запрос `/servers`. Неудачное обновление больше не очищает уже полученный список, а показывает причину и кнопку повтора на главном экране и в шторке серверов.
- **Ссылка подписки.** Если backend возвращает локальный адрес панели (`http://127.0.0.1:2096/sub/...`) или обычный HTTP, клиент запрашивает тот же путь по HTTPS с публичного хоста backend. Токен подписки не логируется. Политика покрыта unit-тестами `SubscriptionUrlPolicyTest`.
- **Вход через Telegram.** Вместо немого диалога показывается экран ожидания с шагами, таймером, кнопкой повторного открытия Telegram и отменой; ожидание увеличено до 5 минут.
- **Устройства.** Верхняя карточка всегда показывает ОС, производителя и модель текущего телефона и отдельно — подтверждён ли он сервером. Остальные устройства показаны списком.
- **Аккаунт и настройки.** Автопродление перенесено в «Настройки аккаунта», помощь убрана из аккаунта, версия — 1.0.0. В настройках остались только рабочие переключатели (автоподключение после перезагрузки, прямой доступ к российским сайтам) и язык.
- **Вопросы.** Содержимое заменено на практические сценарии: фоновая работа, выбор протокола, лимит устройств, перенос подписки, автопродление, зависший вход.

Что по-прежнему не подтверждено:

- Список серверов на телефоне зависит от данных, которые отдаёт backend. Если `/api/v1/servers` и подписка возвращают пустой список, клиент покажет ошибку и повтор, но не выдумает серверы.
- **IPv6 на той версии.** На тот момент TUN создавался только с IPv4-маршрутом. Это историческое замечание; в текущем коде добавлен IPv6-маршрут, но нужна проверка реального IPv6-трафика на устройстве.
- Реальный трафик через TUN, DNS и IPv6, переподключение после смены сети, удаление устройства, оплата и release-подпись не проверены: ADB-устройство отключилось во время работы.

## Проверка серверов на устройстве 31.10.2026

- `GET /api/v1/servers` для аккаунта возвращает `nodes=0` при наличии `subscription_url`.
- Ссылка подписки публичная (`https`, порт 2096), но отдаёт HTTP 404 и без заголовков, и с `X-HWID`, `User-Agent` v2rayNG и другими вариантами. Значит, на панели 3x-ui устарел `sub_id`, а не клиент не умеет его запрашивать.
- `GET /api/v1/subscription/status` для того же аккаунта возвращает `active` и `seconds_remaining=193218180` (около 2237 дней), поэтому карточка подписки права, а список серверов — нет.
- Установленное production-приложение показывает 4 сервера только из локального кэша, сохранённого ранее; его собственный запрос `/servers` тоже возвращает 0 узлов.
- В логах бота видны ошибки фоновых задач `app_tls_server` и `webhook_server`; backend требует ремонта/перевыпуска подписки. Клиент не подставляет вымышленные серверы: он показывает причину и кнопку повтора.
